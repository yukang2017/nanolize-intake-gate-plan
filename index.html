让 nanolize 真正支持非 Python 项目：从入口门禁开始的三步方案

在最新 main 上对公开仓库 morluto/rea 做 nanolize 时，仓库在建结构索引和开始评审两处都被拒绝，原因是 third_party/ 下有 5 个 Git 子模块；同一次运行还给这个 TypeScript 项目建了一个只装 pytest 的 Python 环境。这一页对着最新 main 的代码给出三步修改方案，目标是让 nanolize 真正支持非 Python 项目，三步合成一个 PR 交付。前两步有本地原型，并在 68 个公开仓库上做了只读的入口验证。

结论

  • 目标是真正支持非 Python 项目，交付一个完整的 PR。三步是同一个 PR 的内容，分四个部分做：入口门禁、语言无关的作业路径、Node 和 TypeScript 生态、设计测试和敲除。做到什么算完成、怎么验收、需要确认的四件事，见下一节。
  • 拒绝是有意的设计，不是最新 main 引入的回归，但拦得过宽。规则写在文档里，也有测试固定。它的问题是按目录名判断：同一个没拉取的子模块，放在 vendor/ 下整个作业能跑完，放在 third_party/ 下连评审都开始不了。
  • 第一步：没拉取的子模块改成“记录但不读”。入口改三处，仓库就能进门：原型上 25 个带子模块的仓库有 21 个能开始评审，剩下 4 个被别的规则拦住。作业一侧还有一个根因必须一起修：集成步骤会删掉子模块的空目录。不修的话，仓库进了门，作业会在两种常见情况下失败，交付结果里也没有子模块条目。这是独立评审用作业级探针复现出来的；只看入口会得出“下游已经能处理”的结论，那个结论不完整。
  • 第二步：尽早失败，对非 Python 项目说清楚。输入分支建好时就报告“这个仓库开始不了评审”，不用等环境装完；环境提案标明项目不是 Python 项目；文件数上限只数源码、测试和依赖文件。
  • 第三步：真正支持非 Python 项目。这是这次改动的目标，也是工作量的大头。八处小改动（C1）让非 Python 仓库靠自己的测试完成一个作业；和 Python 对等（C2）的每一项都是大改动，其中敲除、导入表和“导出”证据可以建立在已有的结构索引上，不用引入新的解析器。给作业提供子模块内容（C3）和语言支持无关，不放进这个 PR。
  • 只做前两步，rea 能进门，但默认流程会在提交时被拒两次。阶段 01 的每一步都能给出结果。到提交时，项目自己的测试命令不能直接写成检查，默认做的约定转换又让清单缺 pytest 模板。两处都能靠显式输入避开。这是分段走查的结论，没有在 rea 上跑作业。

三个做法上的决定

  • 加一层“生态”描述，不重写 Python 的逻辑。nanolize 的 144 个源码模块里有 30 个直接用 Python 的语法分析。这些逻辑不动。新增的一层只描述四件事：这个生态怎么装依赖、怎么跑一个测试文件并给出用例报告、测试文件怎么命名、失败输出怎么读。Python 现有的行为是其中一项，Node 是第二项，以后加别的语言是再加一项。
  • 非 Python 语言的语法信息来自结构索引，不引入新的解析器。结构索引已经解析 TypeScript、JavaScript、Rust、Go、C、C++、Java 等语言：每个函数和方法有起止行列、签名、是否导出，文件之间有导入和调用关系。rea 的索引有 170,070 个节点；openai/codex 的索引里 Rust 有 42,895 个函数节点。敲除要的函数范围、导入表、转换要的“导出”证据都可以从这里取。代价是对非 Python 仓库，索引从“默认开”变成必需。设计出来的测试文件不在索引里，它的静态检查用什么解析还要在实现时定：可以对设计目录单独建一次索引，或者只做词法检查
  • Python 仓库的行为不变。每一处改动对 Python 仓库都应该是无操作，用全量测试和 Python 仓库的入口验证守住。默认行为的变化（例如不再转换）只发生在非 Python 的功能上。

验收

  • 入口。68 个仓库的验证重跑：带子模块的 25 个里至少 21 个能开始评审，被智能体工具目录的链接拦住的 3 个放行，vercel/next.js 得到一句理由而不是异常，原来能开始的仓库一个不少。
  • 测试。nanolize 的全量测试通过，每一部分带自己的用例。
  • 真实作业，默认流程，不加绕过用的参数。两个小型 TypeScript 或 JavaScript 仓库跑完整作业；rea 的阶段 01 和提交用整个仓库，作业只选一小组功能，因为它的源码有 100 万行，核心范围的整个作业代价很大；一个 Go 或 Rust 仓库走语言无关的路径；一个 Python 仓库做回归。Claude 和 Codex 两种运行器各至少跑一次。
  • 验收报告。PR 说明附一页：每个作业的结束状态、验证到了什么、没验证到什么。

需要确认的四件事

  1. 范围。建议四个部分都做：Node 和 TypeScript 做到和 Python 对等，其他语言做到第 2 部分的水平。较小的选择是只做第 1 到第 3 部分：非 Python 仓库能用默认流程跑完作业，但验证只靠项目自己的测试，没有设计测试和敲除。
  2. 子模块内容（C3）不放进这个 PR。它和语言支持无关，rea 的核心功能也不依赖子模块。
  3. 验收作业用哪些仓库，可以花多少。真实作业要花智能体调用，是这个 PR 里最贵的部分。
  4. 推送和开 PR 的时机。实现在本地分支上做。可以做完再确认一次才推送，也可以现在就同意做完直接开 PR。

这个 PR 不包含的

  • 其他生态（Rust、Go、Java、C++ 等）的环境准备、设计测试和敲除。这次给它们语言无关的路径，和以后加一项生态描述的位置。
  • 给作业提供子模块的内容（C3）。
  • 走查没有读到的部分：性能验收、任务成本评估和报告站点在非 Python 仓库上的表现。实现前先补走查，有问题的并入第 3 部分。

1. 两个现象和它们的原因

两个现象都在最新 main 上用 rea 的浅克隆复现了（子模块没有拉取，提交 366e1d9）。下面的行号是 main 上的位置，路径省略了 src/nanolize/。

现象一：带子模块的仓库在两处被拒，关掉索引也绕不过

在哪里发生了什么代码位置
快照Git 把子模块列成一个条目，磁盘上它是目录。快照把它记成 not_regular，这一类发现不管选什么功能都拦。rea 有 9,709 个文件，5 条这样的发现，全在 third_party/ 下repository.py:1088分级规则在 repository.py:116
build_code_index返回 unavailable，理由 source_submodule，下一步写明不能不带索引继续understanding.py:403
start_execution_review评审控制器一创建就拒绝：快照不完整。所以 index=off 没有用，拒绝的不是索引而是评审本身execution.py:1855

这是有意的设计。文档 docs/structure-index.md 有专门的一行说明 source_submodule，两个测试固定了它，其中一个用的子模块路径就是 third_party/library。评审拒绝不完整的快照在 11 月初就是这样，source_submodule 这个名字是 11 月 22 日随结构索引加的。

毛病在判断依据。规则按目录名判断，而不是按“这是一个子模块”判断。同一个没拉取的子模块放在三个位置，最新 main 的结果是：

子模块的位置快照来源检查原因
vendor/lib完整接受vendor 在跳过目录名单里，快照根本不看这个路径
third_party/lib不完整source_submodule不在名单里
tests/data/lib不完整source_incomplete注释说测试里的子模块不算，快照照样拦

nanolize 自己的测试里，带子模块的整条作业是能跑完的，只是测试都把子模块放在 vendor/library 和 tests/vendor/lib 下（tests/test_execution.py:148–183、tests/test_codegraph_tool.py:1703）。下游已经为没拉取的子模块做了处理：索引副本为它建空目录（codegraph_tool.py:1154），候选树按提交号绑定它，并拒绝非空的子模块目录（execution.py:1034–1037）。入口是第一道坎。过了入口，作业一侧还有一处要改：集成步骤会删掉子模块的空目录，vendor/ 下不受影响只是因为那个目录不被遍历。见第一步的 A4 到 A6。

现象二：给 TypeScript 项目建了只装 pytest 的 Python 环境

  • 直接原因。propose_test_environment 只读 Python 的元数据文件（pyproject.toml、setup.cfg、tox.ini、各种 requirements 文件）。rea 的根目录一个都没有，它仍然无条件把 pytest 加进建议（test_environment.py:315–322），技能又写着“总是准备测试环境”。对 rea 的返回是：项目名为空，运行依赖为空，建议只有 pytest。
  • 默认流程确实要它，但对这个项目没有用处。作业设计的测试只能是 pytest 文件；默认会做约定转换，转换后的清单里没有 pytest 检查时，提交还要求一个 pytest 模板（execution.py:6446–6462）。所以按默认流程走，这个环境是要用的。但 rea 的功能几乎都不是 Python：关掉测试设计以后，后面没有任何工具需要这个环境。
  • 真正缺的东西。rea 自己的测试用 vitest，需要 npm ci 和 Node 22.23.4 以上。nanolize 没有任何步骤准备这些，返回里也没有一句话提醒这不是 Python 项目。

2. 验证：68 个公开仓库的入口结果

每个仓库浅克隆一份，子模块不拉取，然后分别用最新 main 和原型跑同一个只读探针：取快照，看有没有“不管选什么都拦”的发现，看评审会不会被拒，再做来源检查。结果分三种：评审可以开始并且结构索引可以绑定；评审可以开始但索引不绑定（来源检查拒绝，按现有规则作业不带索引继续）；评审被拒绝。

3. 第一步：没拉取的子模块改成“记录但不读”

目标是让子模块按它本身的状态处理，而不是按所在目录的名字。没拉取的子模块在检出里是一个空目录，它的文件不属于这个仓库，nanolize 不读也不改，只记下路径和它被固定在哪个提交上。已经检出的子模块继续拦，因为目录里有别的仓库的文件。

这一步分两半。入口的三项让仓库能进门；作业一侧的三项必须一起做，否则仓库进了门，作业会在两种常见情况下失败。两半的根因不同，但都很小。

入口：三项

#改什么在哪里原型和验证

作业一侧：三项，同一个根因

根因在集成步骤：它把作者写的文件放进候选工作树之前，会删掉所有空目录（rewrite.py:1881–1883），子模块的空目录也在其中。现在 vendor/ 下的子模块不受影响，只是因为那个目录从来不被遍历。下面三种后果都由对抗性评审用作业级探针复现了。

尝试被什么拦住拦住的方式
作者第一次保存时往子模块目录里写文件候选树绑定只接受空的子模块目录（execution.py:1034–1037）崩溃 A5 改成退回
作者在之后的保存里往那个路径写文件不需要拦：此时它们是普通文件，会被提交、进快照、计入体积不构成隐藏
在候选或原版的工作树里改子模块的提交号候选树绑定记录了提交号，校验时比较拒绝

检查或准备脚本往原版工作树的子模块目录里写东西原版的树绑定崩溃且无法恢复 A5 的回滚改动解决
作者自己写一个 .gitmodules现在没有拦，它被当成普通文件A6 之后归验证方所有
作者自己造一个子模块条目做不到：集成只复制普通文件不可能

有一件事没有任何检查覆盖：作者把子模块上游的代码抄进候选，重合度检查不会发现，因为它只和原版自己的文件比。这样做只会让候选变大，绕不过体积统计。

这一步做完以后仍然成立的限制

  • 作业里永远拿不到子模块的内容。需要子模块才能构建或运行的检查，在原版的基线上就会失败，基线如实记录，不会被算作通过。
  • 准备脚本不能在作业里拉取子模块。在原版工作树里执行 git submodule update 会让那个目录非空，作业随即出错。A5 之后这会是一条说得清的拒绝。真正提供内容是第三步的事。
  • 用户目录里已检出的子模块仍然被拦。但作业用的是输入工作树，那里的子模块总是空目录，按技能的流程走不会碰到这一条。

4. 第二步：尽早失败，对非 Python 项目说清楚

这一步不放宽任何规则的含义，只改三件事的时机和说法，外加验证里新发现的两处。现在的顺序是先准备测试环境（技能的步骤 0，安装上限 60 分钟），到步骤 2 建结构索引时才第一次碰到入口规则。

输入分支调用时已经对用户的目录取过一次快照，那一次不能复用：它描述的是用户的目录，那里的子模块可能已经拉取，而评审看的是输入工作树。但那一次可以省掉：它只用来找“没有提交的源码、测试和依赖文件”，这用一次 Git 列表就能得到，不需要读文件内容。这样总的读盘次数和现在一样。

5. 第三步：真正支持非 Python 项目，和要用子模块内容的仓库

前两步做完，rea 这样的仓库能进门、能建索引，用户也会在一开始就被告知它不是 Python 项目。接下来它会停在哪里，由一个独立的会话对着最新 main 逐步走查：能在 rea 的副本上直接运行的工具都运行了，其余的读代码或者在一个很小的 TypeScript 仓库上试。没有启动评审，也没有跑作业。

走查的结论

  • 门禁修好以后，阶段 01 没有任何一步拒绝 rea。环境提案、证据、结构索引、功能发现、清单、绑定和计划都给出了结果，只是语义分析只覆盖它的 32 个 Python 文件（源码清单共 3,894 个文件）。
  • 下一处确定的拒绝在提交时，有两个，默认流程会一头撞上。一是把项目自己的测试命令 node scripts/run-vitest.mjs … 写成检查会被拒，因为那个运行脚本按 .mjs 后缀算产品源码，而检查不能把产品源码冻结成自己的输入。二是默认会做约定转换，转换后的清单里没有 pytest 检查，就因为缺测试模板被拒。
  • 过了提交没有因为语言而拒绝的地方，但缺三样东西。Node 环境（node_modules 只存在于准备脚本装过的工作树里，验证测试有效性用的导出里没有）；把失败的 vitest 检查反馈给作者的摘要（现在只有编号和状态）；非 Python 的安装检查（没有它，最好的结束状态是 completed_with_gaps）。
  • 知道这一切的操作者，今天不改代码也可能把一个作业跑通。办法是每一步都给显式输入：不做转换，检查写成 npx vitest run …，npm ci 作为准备脚本，关掉测试设计，配置文件逐个声明为原样携带。这是分段验证出来的，没有端到端跑过。

7. 独立核对改了方案的哪些地方

原型和方案交给了四个独立的会话核对，它们只拿到问题，没有拿到答案：一个 Codex 会话（另一个模型）评审补丁并核对 Codex 一侧；一个会话做对抗性评审，专门找原型漏掉和会被利用的地方；一个跑 nanolize 的全量测试；一个走查非 Python 仓库在默认流程里会停在哪里。下面是被采纳进方案的发现。前三条改变了第一步的范围。

8. 没有做的事和要注意的地方

  • 没有跑完整的 nanolize 作业。68 个仓库上只验证了入口：快照、来源检查、输入分支、结构索引。“能开始评审”不等于“作业能跑完”。

  • 克隆的是各仓库当天的默认分支。仓库在变，换一天数字会有出入。rea 的文件数离 10,000 的上限只差 291 个。
  • 第三步的判断来自读代码。没有在任何非 Python 仓库上跑过作业，哪一步会停是按代码和技能文件推断的。
  • 探针在网络文件系统上跑。快照的耗时比本地磁盘慢，B5 的超时在本地磁盘上未必出现。
